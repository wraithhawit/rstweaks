RSTWEAKS / RSPERF - WHAT EACH VERSION DID
=========================================

One or two lines per version, newest first. This file is the short form; CHANGELOG.md is
the detailed history and carries the reasoning. BOTH ARE MAINTAINED - every version bump
gets an entry in each. CHANGELOG.md was backfilled to 0.2.80 on 2026-08-16; the only gap
left is 0.2.18 - 0.2.46, which was never written down anywhere and is recorded there as
one honest block rather than reconstructed.

The mod was called "rsperf" up to 0.2.40 and "rstweaks" from 0.2.41. Searching a log for
"rstweaks" will miss anyone still running an older build.

0.21.1
------
  THE SELF-TEST WAS DELETING THE BENCHMARK IT EXISTS TO PROTECT. The suites build real TaskImpls and
  run them to completion through the real engine -- that is the whole point of them -- so 0.19.0's
  craft timer recorded every fixture scenario as a finished craft. One /rstweaks selftest completes
  a dozen in under a second, and only 8 are kept, so running it evicted the real 10k and 100k
  numbers from /rstweaks stats. Caught the first time Wraith ran the two side by side:
    craft finished: 64 x product in 0ms
    craft finished: 40 x widget in 0ms
    craft finished: 4 x chest in 1ms
  Fixed with a depth counter rather than a flag, because suites nest: SelfTests guards a whole run
  and TaskEngineSelfTest guards itself, so a gametest calling a suite directly is covered too.
  Deliberately NOT synchronized -- the body is a whole suite and takes seconds, and holding the
  monitor across it would block record() from RS's autocrafting threads for the duration. The
  counter is only touched from the thread running the suite.
  Verified by counting: the gametest run now records ZERO fixture crafts, where it previously logged
  a dozen. 34/34 still pass.
  ALSO FROM THAT SESSION: /rstweaks selftest passed 392 checks in the real world, all 12 categories.
  The 100k benchmark read 34.3s (2,916/s) against 0.20.0's 33.6s (2,978/s) -- 2% apart, which is
  inside the run-to-run variance and consistent with 0.21.0 having been test-only. The 10k read
  4.8s (2,067/s) against 3.3s, explained by other crafts running in the world at the time: the
  benchmark is only comparable when nothing else is crafting.


0.21.0
------
  /rstweaks selftest RUNS EVERYTHING NOW; a name after it narrows the run. I had it backwards in
  0.18.0 -- bare selftest ran a partial set of four suites while the full one hid behind a
  subcommand, which is the wrong way round for the command somebody types when they are worried.
    /rstweaks selftest             -> all 12 categories, 392 checks
    /rstweaks selftest crafting    -> the crafting group
    /rstweaks selftest durability  -> one category
  Tab completion lists them, and an unknown name says what the valid ones are instead of failing
  silently.
  CATEGORIES ARE DISJOINT so a full run never executes a scenario twice and the total is a real
  total: planner, lp, maxcraftable, ledger, patterns, executor, remainders, requests, overflow,
  durability, storage, optimizations. "crafting" is a GROUP over eleven of them rather than a
  category, which is why it can overlap without double-counting anything.
  The per-category breakdown prints on a PASS as well as a failure -- "392 checks" says nothing
  about whether the category you cared about actually ran, which is the same class of mistake as a
  counter that is written and never printed.
  The gametest now runs SelfTests.runAll() rather than naming suites itself, so a category added to
  the catalogue is covered the moment it is registered instead of whenever somebody remembers to
  add it in two places.
  Full local battery on 0.20.0/0.21.0: every headless suite green, 34/34 gametests, mutation
  testing 476/696 killed (68%) with 89% line coverage on mutated classes.


0.20.0
------
  THE DURABILITY CACHES MOVE ONTO THE RESOURCE. Five of them -- tool family, damage-stripped
  identity, the resource one use further worn, maximum damage, default damage -- were each a
  ConcurrentHashMap keyed on ItemResource. Profile mWcYLBc220: ConcurrentHashMap.get is 12.64% of
  the server thread, up from ~1% before 0.17.0 added the third. Individually cheap, and asked an
  enormous number of times.
  An ItemResource is immutable, so an answer derived from one can live on it. RS already does this
  with its own private int hash, which is the precedent for both the idea and the race.
  I ALSO CORRECTED WHAT I TOLD WRAITH. I said this would remove HashMap.hash (21.27%) plus
  ItemResource.equals; the --parents breakdown says HashMap.hash comes from getNode/put/remove on
  RS's OWN resource lists, which no cache of ours can touch. The addressable figure is the 12.64%,
  not 28%. Checked before building rather than after.
  SENTINELS RATHER THAN FLAGS. Mixin does not run field initialisers reliably, so every field has to
  mean something when it defaults to zero: ints are stored offset by one, and 0 always reads as "not
  worked out yet". Racy on purpose and safe for it -- every field is a pure function of an immutable
  object, so two threads racing compute the same value and the worst case is doing it twice. A
  volatile would put a barrier on the hottest path in the mod to prevent something that cannot
  happen.
  FALLS BACK, NOT BREAKS. Every call site is an instanceof against ResourceMemo; if the mixin does
  not apply, ItemResource stops implementing it and every answer goes back through the map it used
  before. Behaviour is identical either way, which is exactly why it needed its own test: a silent
  failure to apply costs 12.64% and changes nothing observable. New gametest asserts the interface
  is there AND that a real question populates the field -- maxDamage=1561, usesLeft=1549.
  ItemResource is final, so the instanceof needs a cast through Object; javac rejects it otherwise.


0.19.0
------
  CRAFTS ARE TIMED NOW, because a share of the server thread cannot measure any of this. Every
  performance figure in this file is a percentage of tickNode, and the multiblock crafter has NO
  TIME BUDGET -- it expands to fill the tick, so making a step cheaper raises the number of steps
  rather than lowering the share. "The durability path went 40.15% to 26.87%" describes a
  redistribution, not a saving, and three of my predictions this session were wrong for exactly
  that reason.
  Wall-clock time for a known craft has none of that problem. Ask for a million insanium on two
  builds and the difference is the answer: no profile, no denominators, no interpretation.
    [rstweaks] craft finished: 1,000,000 x mysticalagriculture:insanium_essence in 4m 12s (3,968/s)
  Logged on completion and kept as the last 8 in /rstweaks stats. A short history rather than a
  running mean, because craft durations vary by orders of magnitude with what is being made and an
  average across different recipes means nothing -- the comparison that works is the same craft
  against itself.
  Hooked on TaskImpl.updateState, since every completion path goes through it. nanoTime rather than
  RS's own startTime: monotonic, so a clock adjustment mid-craft cannot produce a negative duration.
  Says "finished" rather than "crafted" because a cancelled task completes too.
  CONFIRMED FIRING in the gametests -- "craft finished: 64 x slimeball in 1ms (64,000/s)" -- which
  is the check this project keeps needing, having shipped four things whose presence was
  indistinguishable from their absence.


0.18.0
------
  /rstweaks selftest crafting -- EVERY CRAFTING SUITE, THEN EVERY OPTIMIZATION OFF AGAINST ON.
  392 checks. The suites answer "does crafting work"; the differentials answer the question that
  actually matters after a run of changes to RS's core loop: does it still work the same with each
  optimization switched on. Every scenario passes with them off -- that is what the fixture is for --
  so each differential ALSO asserts its counter moved. If the optimization never fired, the ON run
  was the OFF run again and it says so instead of going green.
  IT FOUND TWO REAL GAPS ON ITS FIRST RUN, which is the whole argument for it:
  1. reuseFailedSimulate and skipUnchangedSteps NEVER ENGAGED in the fixture. Both need a repeated
     ask with an UNCHANGED world, and at StepBehavior.DEFAULT's one step per call a blocked pattern
     failed once, a sibling executed, storage changed, and the caches correctly declined. A real
     crafter asks for up to 175,552 steps a tick, so one pattern is stepped thousands of times with
     nothing else touching internal storage. The fixture now steps 4 per pattern per call, which is
     the real shape rather than a special case.
  2. skipUnchangedSteps SUBSUMES reuseFailedSimulate. Once the step returns IDLE up front,
     extractAll never runs and the substitution inside it is unreachable, so the replay cannot fire.
     Not a conflict -- the outer skip is strictly better where it applies -- but the replay is only
     reachable, and only testable, with the skip out of the way, and it remains the fallback
     whenever skipUnchangedSteps is off. The differential isolates them for that reason.
  NEW SCENARIO: "tool pattern blocked behind another pattern". Only a pattern with a durable
  ingredient records a decision, and until now every tool scenario could run on its first ask -- so
  the fixture contained ZERO repeated failing simulates, measured, which is why three optimizations
  shipped with no coverage and needed in-game verifiers instead. The tool pattern now waits on a
  gear it cannot have yet. The simulate-repeat probe went from 0 to 121 repeats, 121 agreed.
  Wired into the gametests too, so the command cannot rot: a command somebody reaches for before
  trusting a build with real items in it is worth more than a command that used to work.


0.17.0
------
  BYPRODUCT AGING WAS THE LARGEST THING LEFT, AND MOST OF IT WAS OURS. 0.16.0 landed: 408,664,800
  steps skipped whole, durability path 31.03% -> 26.87% (profile ajw2GTmG3M), verified at 442,767,424
  checks and 0 divergences. With whole steps gone, what remains concentrates in the steps that do
  execute -- and tryKeepByproductsInTask came out at 31.58% of the server thread, with
  InternalTaskPattern.aged 27.68% inside it:
    ItemDurability.afterUses    51.87% of aged  = 14.4% of the server thread   OURS
    wearStep                    21.10%          =  5.8%                        RS
    rstweaks$consumedTool       18.83%          =  5.2%                        OURS
  afterUses built an ItemStack, copied its component map and rebuilt an ItemResource on every call,
  to compute something completely determined by its input. Now cached for uses == 1, which is what a
  wear step asks for; anything else allocates as before.
  KEYED ON THE RESOURCE, NOT ON (item, damage). The aged resource is built from the old one's stack,
  so it carries the whole component patch forward -- an (item, damage) key would hand a named or
  enchanted tool the plain tool's answer and silently strip its components mid-craft. That is the
  issue-9 family of bug. New scenario pins exactly that collision, and BREAK-TESTED: keying on Item
  fails "a named tool does not age into the unnamed one" and "the name survives aging"; keying on
  the resource passes all 209.
  The tool-breaks case is deliberately not cached -- once per tool, and that path allocates nothing
  anyway; caching it would mean a null sentinel to speed up the rare branch.
  consumedTool got 0.12.0's hoist, which it never received: it resolved the encoded side's family
  once per entry in the consumed list instead of once for the loop.
  Both changes are ours, both are pure functions of immutable inputs, and neither touches RS's core.


0.16.0
------
  SKIP THE WHOLE STEP, NOT JUST OUR PART OF IT. Profile L7lGOu8YyD: 0.15.0's replay works exactly as
  designed (236,864,784 decisions replayed of 322,780,160 calls, 73.4%, dead on the ceiling) and
  bought 1.01 points -- 32.04% -> 31.03%. I predicted more than 0.14.0's 4.24 and was wrong for the
  third time; the reason is a floor, not a mistake. replayDecision alone is 10.42% of the server
  thread for 236.9M replays: ~53ns each, on a method called 2.7 MILLION TIMES A SECOND. At that
  volume no per-call work is cheap, so the next win cannot come from making the call cheaper.
  InternalTaskPattern.step returns IDLE the instant extractAll(SIMULATE) is false, having done
  nothing else. When internal storage has not changed since such a step it reaches the same
  conclusion by the same route, so returning IDLE up front is not an approximation of RS -- it is
  what RS does. That also skips calculateIterationInputs (28.24% inclusive) and extractAll (34.56%),
  which no cache inside our own mixin could ever reach.
  VERIFIED IN THE 2.0.9 BYTECODE, because the whole idea rests on a failed simulate having no side
  effects: calculateIterationInputs' mutating branch is gated on Action.EXECUTE; step returns before
  touching outputs, byproducts, wear or the root storage; and TaskImpl.stepPatterns only asks whether
  the result is COMPLETED and whether isChanged(), so IDLE is its ordinary no-change path.
  RETURNS A VALUE IT CANNOT NAME. PatternStepResult is package-private, so StepSkipMixin captures the
  IDLE instance from a real return, recognising it by Enum.name(), and hands that same object back.
  Fail-safe in the right direction: until an IDLE has actually been observed nothing is ever skipped,
  and a rename upstream ends the optimization rather than breaking it.
  SHIPS WITH ITS OWN VERIFIER AGAIN. verifyStepSkip (default off) lets every skippable step run and
  asserts it really did return IDLE. The same discipline cleared 0.15.0's replay at 118,470,766
  checks and 0 divergences, which is stronger evidence than the fixture could ever give -- the
  task-engine suite has no repeated failing simulates in it by construction.
  Mixin confirmed applying to InternalTaskPattern; 32 gametests pass including the task engine.
  VERIFIED IN GAME 2026-08-30: 442,767,424 skippable steps allowed to run and checked, 0 DIVERGED.
  Every one really did return IDLE. Same discipline, same result as 0.15.0's replay at 118M/0.


0.15.0
------
  THE LOOP WAS THE COST, NOT THE SCAN. 0.14.0 skipped the storage scan on a repeated failing
  simulate and left the machinery around it running. Profile m4dQmEhBRW: findWornTool is down to
  1.60% of the server thread while trySubstituteWornTool is 31.82% -- self 30.46% of that, plus
  getAll 5.19%, get 3.21%, isDurable 1.24% and rememberedSubstitute 2.00%. Walking every input and
  asking a map about each one, to arrive at an answer already in hand.
  A valid repeat now REPLAYS the whole decision instead of re-deriving it: restore the consumed
  list, apply the remembered swaps, return. No walk, no durability question, no per-ingredient
  lookup. The swaps still have to be applied because calculateIterationInputs builds a fresh input
  list every step.
  THE CONSUMED LIST IS COPIED, NOT ALIASED. rstweaks$consumed is cleared at the top of every call,
  so keeping a reference would replay an empty list -- and an empty consumed list means byproducts
  come back as encoded, which is a repaired tool: durability created from nothing, the 0.2.57 bug.
  NO TEST CAN COVER THIS, AND THAT IS THE HONEST PROBLEM. The task-engine fixture treats a step that
  makes no progress as a deadlock and fails the scenario, so it contains ZERO failing simulates by
  construction -- measured, not assumed. A change on the item-correctness path with no coverage is
  not something to ship on reasoning.
  SO IT SHIPS WITH ITS OWN VERIFIER. verifyReplayedDecisions (default off) recomputes every replayed
  decision and compares both the swaps and the consumed list, logging the first 20 divergences. It
  costs the entire saving while it runs; the point is to answer the question. Anything other than
  "0 diverged" means reuseFailedSimulate comes back out.
  Counters are now a matched per-CALL pair (decisions replayed / decisions computed) rather than
  mixing a per-call numerator with a per-resource denominator, which would have produced a confident
  nonsense percentage.
  VERIFIED IN GAME 2026-08-30: 118,470,766 replayed decisions recomputed and compared, 0 DIVERGED --
  swaps and consumed list both, on a real insanium craft. Stronger evidence than any fixture could
  have given, which is the point of shipping the verifier rather than the reasoning.

0.14.0
------
  THE FAILING SIMULATE IS CACHED, AND THE 1,052 ARE HANDLED EXACTLY RATHER THAN GAMBLED ON.
  0.13.3's diagnostic answered the open question outright: in every logged disagreement the WANTED
  key was identical and what moved was storage. The crystal wears, a more-worn level appears, and
  findWornTool's "most worn first" rule flips the pick -- fresh, then @275, then @494. One case went
  from NO SUBSTITUTE to a substitute, which a blind cache would have turned into a craft that
  refuses to run. calculateIterationInputs was ruled out; it never handed back a different wanted.
  Every one of those is a mutation of the task's internal storage. So MutableResourceListImplMixin
  counts them -- add, remove, clear -- and a failing simulate reuses the previous answer only while
  the storage version AND the input count are unchanged. Two O(1) reads, exact rather than
  statistical, and it invalidates on precisely the 1,052.
  THE PRIZE: 169,947,478 repeated failing simulates measured on a real insanium craft, one pattern
  rescanning the task's whole internal storage 701,697 times in a row. ~73% of iterations fail their
  simulate, which is why the execute-side cache could only ever reach a fifth of the scans.
  SAFE BY CONSTRUCTION, NOT BY THE MIXIN LANDING. A storage that does not implement
  VersionedResourceList reuses nothing and rescans exactly as before. reuseFailedSimulate (default
  on) switches it off. Ignored while either probe runs, so a probe never measures a cache against
  itself.
  MIXIN PROVEN TO APPLY, AND BREAK-TESTED. New gametest builds a real MutableResourceListImpl,
  asserts it implements VersionedResourceList, and exercises add, remove and clear SEPARATELY --
  0 -> 3. Deleting the increment from the remove injector fails that test by name; restoring it
  passes all 32. A counter that applies but misses a mutation is the one way this design is wrong
  rather than merely useless, so each mutation is pinned on its own.
  UNMEASURED IN GAME: the fixture has zero failing simulates, so no automated test can show the
  cache firing. /rstweaks stats reports failedSimulateScansAvoided; that number and a profile are
  what will say whether this was worth it.


0.13.3
------
  WHAT ARE THE 464? 0.13.2's probe, on a real insanium craft: 75,360,365 repeated failing simulates,
  75,359,901 agreed, 464 disagreed, and a LONGEST FAILING STREAK OF 701,697 -- one pattern rescanning
  the task's whole internal storage seven hundred thousand times in a row for the same answer. The
  payoff is enormous and the invariant is 99.99938%, which is exactly the shape that gets a wrong
  answer shipped because the number looked close enough.
  TWO CAUSES WOULD PRODUCE 464 AND THEY NEED DIFFERENT FIXES. (1) Internal storage changed: RS steps
  many patterns per tick inside one task, so a sibling executing mutates the shared storage and this
  pattern's next simulate legitimately sees a different world -- fixable by versioning the storage.
  (2) The inputs changed: calculateIterationInputs is recomputed every step and takes the Action, so
  the WANTED wear level itself can differ between two simulates -- versioning storage would not catch
  that at all. I had inferred (1) and had shown neither.
  So a disagreement now logs both decisions with, for every resource named on either side, what
  internal storage holds and what the inputs ask for. A differing wanted key points at cause 2; equal
  keys with different amounts point at cause 1. Capped at 20 lines -- this is the hottest path in the
  mod, and a rare event logged without a bound is how a diagnostic becomes the outage.
  Rides on simulateRepeatProbe, no new config. No behaviour change.
  NOT BUILDING THE CACHE YET. On these numbers it is worth roughly four times what the execute-side
  reuse was worth, and it needs a new mixin on RS's MutableResourceListImpl to be exact rather than
  statistical. Worth knowing the cause first.


0.13.2
------
  THE REUSE IS PERFECT; THE CEILING WAS THE RATIO. 0.13.1's counters, from a real insanium craft:
  "33,271,287 scans avoided of 33,271,287 eligible (100.0%); missed 0 nothing-remembered,
  0 revalidation-failed; 125,013,928 not eligible". The execute-side cache never misses.
  MY 0.13.0 READING WAS WRONG. I inferred a ~1% hit rate from a profile instead of counting it. The
  fast path was always working; what is small is the share of calls it can reach. "Not eligible" can
  only be the SIMULATE pass, so the real ratio is 3.76 SIMULATES PER EXECUTE -- InternalTaskPattern
  .step returns IDLE when extractAll(SIMULATE) is false, so ~73% of iterations fail their simulate
  and never execute. The cache could only ever reach a fifth of the scans, and it collects all of it.
  That is why 0.13.0 moved 0.75 points: it did everything available to it.
  SO THE TARGET MOVES to the other four fifths. RS re-steps one pattern up to 175,552 times a tick,
  so a pattern that cannot proceed rescans the task's whole internal storage for an answer that has
  not changed. New simulateRepeatProbe (default OFF, does NOT disable the execute cache -- different
  passes) counts whether consecutive failing simulates reach the same substitution, and the longest
  failing streak, which is the payoff figure: a cache saving one rescan is not worth writing.
  Detected with no new state: rstweaks$simulatedSwaps is nulled by every EXECUTE, so finding it
  still populated at the top of a SIMULATE means the previous simulate was never consumed.
  HONEST ABOUT COVERAGE: the fixture produces ZERO repeats, measured -- every task-engine scenario
  is built so its patterns can proceed. The gametest pins that repeats reconcile as agreed plus
  disagreed and explicitly does not claim to prove the probe fires. Only a real craft can.
  No behaviour change.


0.13.1
------
  0.13.0 UNDERDELIVERED AND I COULD NOT SAY WHY. Profile 2Dwcfddcxn (0.13.0, 1M insanium): the
  durability path went 37.03% -> 36.28%, against an arithmetic prediction of ~28% off it. The tree
  says why it fell short but not why THAT happened: findWornToolReusing spends 94.67% of itself

0.13.0
------
  THE PROBE CAME BACK CLEAN, SO THE CACHE IS BUILT. On a real 1M insanium craft, 0.12.1's probe
  measured 63,247,889 SIMULATE/EXECUTE pairs, 63,247,889 agreed, 0 disagreed, 0 execute-without-
  simulate. RS runs every iteration twice and SIMULATE does not mutate internal storage, so the
  second findWornTool walks the same storage for the same tool.
  findWornTool was 57.24% of this mixin's 37.03% of the server thread (profile IiXxJ4Mk4j). The
  EXECUTE pass now reuses the substitute SIMULATE chose, so half those walks are gone.
  SIXTY-THREE MILLION AGREEMENTS IS EVIDENCE, NOT A PROOF, and it is not trusted blindly. The
  remembered substitute is re-validated against internal storage with one O(1) lookup before use;
  a resource that was not in the remembered decision, a substitute no longer present in the amount
  needed, or an EXECUTE with no SIMULATE in front of it all fall through to the full scan. The fast
  path can only return an answer the slow path would also have returned. reuseSimulatedSubstitution
  (default on) switches it off and restores the double scan exactly.
  The probe DISABLES the cache while it is on -- with the cache serving EXECUTE the probe would
  compare the remembered answer against itself and report agreement no matter what. A measurement
  that cannot fail is not a measurement.
  BREAK-TESTED. New differential gametest runs the task engine with the reuse on and asserts
  substitutionScansAvoided moved (83 scans across 6 scenarios) -- without that counter the run
  would just be the rescanning run again. Returning the wrong half of the remembered pair makes a
  required test fail; restoring it makes all 30 pass.
  UNMEASURED IN GAME: the arithmetic says this removes ~28% of the durability path, but the last
  four versions all had sound arithmetic and moved the total by ~1.5 points each. Profile it.


0.12.1
------
  THE PROBE FOR THE BIGGEST REMAINING WIN. Profile IiXxJ4Mk4j confirms 0.12.0 worked -- maxDamage
  8.86% -> gone, HashMap.hash 22.74% -> 20.12%, ItemResource.equals 11.90% -> 9.95%, durability
  path 38.82% -> 37.03% -- and the 2.0.9 bytecode of InternalTaskPattern.step shows where the real
  duplication is: calculateIterationInputs(SIMULATE) + extractAll(SIMULATE) to TEST an iteration,
  then the identical pair with EXECUTE to DO it. Our substitution therefore scans the task's whole
  internal storage twice for one iteration's work, and SIMULATE does not mutate storage.
  Caching the first answer for the second pass would halve 37% of the server thread -- IF the two
  passes always agree. calculateIterationInputs takes the Action, so it is entitled to differ, and
  assuming otherwise is exactly the mistake 0.11.2 made ("almost every candidate is a different
  item" -- true in general, false for the only case that mattered).
  So this MEASURES the invariant rather than assuming it. New substitutionProbe config, default
  OFF, changes no behaviour: it compares the SIMULATE swap decision against the EXECUTE one and
  counts agreements, disagreements, and execute-without-simulate. Read it with /rstweaks stats.
  A disagreement count of zero over a long real craft is what would justify building the cache.
  AND IT IS PROVEN TO FIRE. New gametest asserts the counters move and that every pair is
  classified -- 89 pairs, 89 agreed in the fixture. The probe only writes on the EXECUTE half, so
  "on but never reached" and "off" look identical, and this project has now shipped three things
  whose presence was indistinguishable from their absence. The gametest deliberately does NOT
  assert zero disagreements: that is the fixture's answer, not the game's.

  Three things the last clean profile (evmko3bHZl, netherrack, batching off) pointed at.
  BATCHING IS THROUGHPUT-NEUTRAL NOW. 0.10.3 capped it per tick, but that bolted a bound on rather
  than fixing the mistake: a batch of N consumed ONE of RS's steps, multiplying per-tick work. A
  batch of N now CREDITS THE NEXT N-1 calls to step() and returns them immediately without work, so
  it costs N steps exactly as N serial iterations would. Same work per tick, one extraction instead
  of N. Cannot repeat the freeze because the arithmetic no longer allows it.
  maxBatchedIterationsPerTick is therefore a BACKSTOP now, not the primary bound; raised 8192 ->
  65536 since blunting it no longer buys safety. This is the fix I should have written first --
  replacing stepPattern's loop was the obvious way and I rejected it as invasive; crediting gets
  the same result without touching a package-private return type.
  DURABILITY STANDS DOWN WHEN NOTHING IS DURABLE. trySubstituteWornTool runs twice per iteration and
  was 3.57% of the server thread on a craft with NO tools in it -- an allocation and a walk of every
  ingredient to conclude there was nothing to do. Decided once per task pattern, read off the
  INGREDIENT BUDGET not the layout (the planner can allocate crystal@50 for a pattern encoded with
  crystal@0, so the layout would miss the very substitution the mixin exists for).
  RS'S PER-ITERATION DEBUG LOGGING. Six LOGGER.debug calls per crafting iteration, ~10^5 a tick;
  with debug logging on (ATM10 default) they are formatted and WRITTEN. CompositeFilter.filter alone
  was 4.85% of the server thread. quietTaskLogging (default on) raises those two loggers to INFO;

0.10.3
-----
  BATCHING FROZE A WORLD FOR 114 SECONDS. A netherrack craft -- the first craft batching ever
  accepted -- produced a single tick of 114,516ms. ModernFix's watchdog thread dump named it:
  HashMap.merge <- rstweaks$tryBatch line 641 <- batchStep <- step <- TaskImpl.stepPattern.
  THE MISTAKE: TaskImpl.stepPattern is `for (i=0; i<steps; i++) pattern.step(...)` and STEPS IS RS'S
  THROUGHPUT BUDGET FOR THE TICK (~10^5 from a multiblock crafter). A batch made ONE of those calls
  do up to 1024 iterations while still consuming ONE step, so per-tick work was multiplied by the
  batch width: up to 10^8 where there had been 10^5. Batching is meant to buy fewer extractions for
  the same work; I removed the throttle instead.
  Invisible until now because the crystal chain has byproducts and batching refused every pattern.
  Netherrack was the first chain it could accept and it took the lot on the first tick.
  FIX: maxBatchedIterationsPerTick, default 8192, refilled per server tick and drawn down by every
  batch across every task. When it runs out batching stands down and RS's stepping continues,
  bounded by steps as always. Deliberately LOWER than what serial does in a tick, so this cannot
  increase per-tick work under any setting.
  The right long-term hook is stepPattern itself, where a batch of N would consume N of steps and be
  throughput-neutral. Bigger change, riskier place, not what a frozen world needs first.
  IF RUNNING 0.10.2 OR EARLIER WITH batchedExecution=true, TURN IT OFF.

  Block pick, out of the network. refinedmods/refinedstorage-quartz-arsenal#4, the other half of
  the pair 0.4.0 came from. In survival, vanilla's pick-block key can only reach into your own
  inventory -- Minecraft.pickBlock calls findSlotMatchingItem, gets -1, and does nothing. That -1
  is the whole feature: with a Wireless or Portable Grid on you, that case now takes a stack out
  of the network. Deliberately NOT tied to the Inventory Interface filter, because that filter is
  a standing instruction about what to do while nobody is looking and this is a key you pressed
  about the block in front of you. A CLIENT MIXIN because NeoForge 21.1 fires no event around
  pickBlock, and it deliberately DOES NOT CANCEL -- the case it acts on is the one where vanilla
  does nothing anyway, so the original still runs and this injection cannot be why pick block
  stops working. The packet carries WHERE the player was looking, not what they want: the server
  derives the item from its own copy of the block, checks the chunk is loaded and that the player
  can reach it with Minecraft's own canInteractWithBlock, then applies the ordinary rules
  (resolvable grid, EXTRACT permission, energy charged at RS's rate). A client that sent an item
  stack could have asked for anything with any components on it. Nothing is overwritten: vanilla's
  creative setPickedItem writes over the selected hotbar slot when it cannot move its contents,
  which costs nothing in creative and would destroy something you mined here, so the destination
  is chosen BEFORE anything is extracted and a full inventory refuses the pick. Four gametests,
  three of them about refusing; the full-inventory one was confirmed to fail with vanilla's
  overwrite put back. 22 pass. The client mixin cannot be gametested -- it needs a client launch.

0.4.0
-----
  The Inventory Interface, and the first thing this mod adds rather than makes cheaper.
  refinedmods/refinedstorage-quartz-arsenal#3, open upstream since RS2 started and labelled
  art-necessary, which is why it never moved -- Refined Storage already ships every sprite it
  needs except two. A Wireless or Portable Grid now files items away and restocks you while it
  sits in your inventory. Sneak + right-click in the air to configure. ONE filter list of nine
  slots, and the amount on a slot means the same thing in both directions: how many to keep on
  you. Auto-insert in ALLOW files away the listed resources beyond their amount; in BLOCK it
  files away everything NOT listed and leaves the list alone entirely; auto-export tops the list
  back up to its amount and reads the list whichever mode it is in, because topping up is a
  whitelist by nature -- which is what makes BLOCK + export coherent ("these are mine, do not put
  them away, and keep me stocked with them") rather than contradictory. Both on is a maintained
  stock. Auto-insert refuses the held item, armour, the offhand and any other grid, and by
  default the whole hotbar (inventoryInterfaceInsertFromHotbar). Compatible with Quartz Arsenal's
  Wireless Crafting Grid and Universal Grid's Wireless Universal Grid, by an ALLOWLIST OF IDS
  rather than a class test: nothing references a class from either mod, so neither is a
  dependency and an unknown addon grid is a config line rather than a build. The gesture is a
  PlayerInteractEvent listener for the same reason -- a mixin on AbstractNetworkEnergyItem.use
  would have covered RS's own grids and silently not run for the two addons, which both override
  it. Everything under the screen is Refined Storage's: filter slots and their packets, the
  filter-mode and fuzzy buttons, generic_filter.png, and both storage paths. This mod registers
  two things, both in its own namespace: a data component and a menu type. Four new gametests
  drive it through a real event on the real bus against a real disk; 17 pass. The first draft of
  those tests waited for PlayerTickEvent instead, which never arrives -- a gametest's mock player
  is placed but never ticked, so the tests reported a feature that did nothing.

0.2.123
-------
  stepRequesterCalculationBudgetMs (default 200): THE FIVE-SECOND FREEZE IS FIXED. RS gives every
  calculation 5,000ms of the SERVER thread. craftingCalculationTimeoutMs could always have cut
  that and deliberately never did, because a cancelled calculation reports MISSING_RESOURCES and
  a global cut would silently refuse a player's valid craft. That reasoning holds for a player
  waiting on an answer; it does not hold for automation, which is not waiting and asks again on a
  schedule anyway. So the budget applies ONLY to Step Requester calculations -- players keep the
  full 5,000ms untouched -- and it ESCALATES per slot on cancellation up to RS's own timeout, so
  a large-but-valid craft is planned after a few attempts instead of never. Any cheap success
  resets it. Worst case for automation: 200ms, four ticks. New chat line "N long calculations cut
  short". backoffCheck 73 -> 90, including the token on a driven clock.

0.2.117
-------
  sortPatternsByPriority: the ROOT CAUSE of the whole session. RS 2.0.9 keeps each output's
  patterns in a PriorityQueue and reads them with holders.stream() -- and PriorityQueue
  guarantees order only for its HEAD, so every alternative after the first comes back in raw
  heap-array layout, which depends on the sequence patterns were added in. CraftingTree tries
  them in that order and explores each failure to exhaustion, so an arbitrary order is an
  arbitrary cost. Re-adding patterns (moving them into one provider) reshuffles every heap:
  same patterns, 0.199 -> 20.249 ms/tick. Now sorted by priority, tie-broken on the pattern's
  UUID rather than an insertion counter, so a pattern keeps its place when it MOVES. New
  patternOrderCheck (29) plus a gametest against RS's real repository (10 total), confirmed to
  fail with the sort off: "insertion sequence 1 produced a different search order".

0.2.106
-------
  A fluid the network holds billions of could not be picked up, and the tank got stored instead
  (#17; ~2.1 MB of XP fluid from a Just Dire Things experience holder). RS's canExtract offers
  the container the ENTIRE network total and fillContainer narrows it to an int, so past

0.2.95
------
  CORRECTION to 0.2.93's diagnosis, no behaviour change. The duplicate-task flood does NOT
  need a regulator upgrade, which is what 0.2.93 claimed. The common cause is the network
  not being able to craft as many as the exporter asks for: RS clamps the request to what

  regulator. `waitForRunningCraft` already fixed both; only the config text, the mixin
  comment and the tests were wrong about why.
