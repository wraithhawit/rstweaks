RSTWEAKS / RSPERF - WHAT EACH VERSION DID
=========================================

One or two lines per version, newest first. This file is the short form; CHANGELOG.md is
the detailed history and carries the reasoning. BOTH ARE MAINTAINED - every version bump
gets an entry in each. CHANGELOG.md was backfilled to 0.2.80 on 2026-08-16; the only gap
left is 0.2.18 - 0.2.46, which was never written down anywhere and is recorded there as
one honest block rather than reconstructed.

The mod was called "rsperf" up to 0.2.40 and "rstweaks" from 0.2.41. Searching a log for
"rstweaks" will miss anyone still running an older build.

0.3.1
-----
  The external storage PROVIDER layer now has gametest coverage; it had none. Found by
  diffing "Mixing <X>Mixin" out of a runGameTestServer log against the mixin package: 22 of
  32 mixins actually loaded, and five of the ten that did not target Refined Storage itself.
  Mixin APPLICATION failure was already loud -- every config sets required:true with
  defaultRequire 1 -- but a mixin that applies and never runs was invisible, which is exactly
  what Cable Tiers once did to us. New ExternalStorageProviderGameTest builds a creative
  controller, a Crafting Grid, an External Storage facing a vanilla chest, and checks that
  items serve and insert through the composite and that the chest really changes. The
  assertion that matters runs the same request with skipMismatchedStorageTypes on and off and
  demands the identical answer -- an optimization that changes an answer is not one. Three
  mixins went from never-loaded to covered: CompositeExternalStorageProvider (a @Redirect on
  BOTH extract and insert, the same layer that destroyed items up to 0.2.55) and the item and
  fluid provider type declarations. The first draft of the equivalence test was WRONG and
  failed against a working mixin: it extracted an item, and the composite returns on the first
  provider that yields anything, so it short-circuited at the item provider and never reached
  the fluid one. Extracting a fluid from a chest is the faithful case and the one actually
  measured in the wild. All 13 gametests pass. No gameplay change.


0.3.0
-----
  Mutation testing, and the test gaps it found. No gameplay change: the mod behaves exactly
  as 0.2.125 did. `./gradlew mutationTest -PpitTarget='<glob>'` runs PIT over a package,
  breaking our own code on purpose to see which breakages no test catches. Three obstacles
  had to be cleared first and are documented in build.gradle: PIT cannot drive a main() that
  System.exits, so a JUnit source set now sits beside the Headless*Check tasks (which are
  unchanged); PIT's globs sweep in the mixins and loading one outside a Mixin environment
  kills its minion; and pitest-junit5-plugin drags in an older JUnit Platform that wins over
  ours. HeadlessBackoffCheck, HeadlessPatternOrderCheck and HeadlessTraceCheck now expose
  run() returning a Result, the shape PatternOrderSelfTest already used, so their 145
  scenarios can be measured. It found FOUR real test gaps, now closed: Rational had no
  direct tests at all and the plan scenarios work in whole numbers, so exact fractions and
  sign normalisation were unpinned; BranchAndBound could drop the push of its second child
  and still return a valid-but-costlier plan; SlotBackoff could drop applyCostFloor on the
  slow-SUCCESS branch, the branch the class exists for; and BudgetedCancellationToken never
  checked that cancel() reaches the delegate. It found NO code defects -- everything it
  pointed at was correct, just unguarded. 49 JUnit tests, 71% mutants killed across
  planner+backoff+pattern+gate.


0.2.125
-------
  Two of our addon tweaks were SHIPPED UPSTREAM by their author, so they now stand down on
  their own. Step Crafter 1.21.1-0.1.7 ("Improved Step Requester performance by adding a
  timeout on failed requested crafts") is our backoff; Cable Tiers 1.21.1-0.6.14 ("Improved
  performance of sided input") hoists the same invariant our lookup did. Both our mixins
  still APPLIED on those versions and both fully replace his implementation -- ours inject
  at HEAD and cancel -- so his new code, and any correctness fix in it, never ran.
  Step Crafter was worse than redundant: 0.1.7 treats a null from get(slot) as "empty slot,
  clear its timeout", and our redirect returns null for exactly the slots we sleep, so we
  reset his backoff every sleeping tick and his timeout could never accumulate. Silent, no
  crash. New AddonMixinGate (an IMixinConfigPlugin) reads the loaded version from
  LoadingModList -- ModList means nothing that early -- and skips the mixin from the
  superseding version on. Older installs keep our fix, deliberately: not every ATM10 is up
  to date and this mod stays drag-and-drop. An unreadable version APPLIES the mixin and
  warns, because silently withdrawing an optimization is the one outcome this mod refuses.
  Version comparison is hand-written and tested: string order puts 0.6.9 ABOVE 0.6.14 and
  Maven treats everything past the dash as one qualifier, and either mistake would leave the
  mixin applied on the exact release that supersedes it. New gateCheck (18), wired into build.
  The startup line no longer claims a stood-down tweak is running.


0.2.124
-------
  stepRequesterCalculationMaxBudgetMs (default 1000): closes the hole 0.2.123 left. Its escalating
  budget capped at RS's own craftingCalculationTimeoutMs, so the ladder's TOP RUNG was still a
  full five-second freeze -- measured climbing 200 -> 400 -> 800 -> 1,600 -> 3,200 -> 5,005ms on
  one repeated request. Bounding how OFTEN a freeze happens is not the same as fixing it.
  Automation now has its own ceiling well under RS's, so the worst an automated calculation can
  cost is 20 ticks. Cost: a craft needing more than 1s to PLAN is never started by automation --
  still craftable by hand, and "long calculations cut short" says when it happens.
  backoffCheck 90 -> 96.
0.2.123
-------
  stepRequesterCalculationBudgetMs (default 200): THE FIVE-SECOND FREEZE IS FIXED. RS gives every
  calculation 5,000ms of the SERVER thread. craftingCalculationTimeoutMs could always have cut
  that and deliberately never did, because a cancelled calculation reports MISSING_RESOURCES and
  a global cut would silently refuse a player's valid craft. That reasoning holds for a player
  waiting on an answer; it does not hold for automation, which is not waiting and asks again on a
  schedule anyway. So the budget applies ONLY to Step Requester calculations -- players keep the
  full 5,000ms untouched -- and it ESCALATES per slot on cancellation up to RS's own timeout, so
  a large-but-valid craft is planned after a few attempts instead of never. Any cheap success
  resets it. Worst case for automation: 200ms, four ticks. New chat line "N long calculations cut
  short". backoffCheck 73 -> 90, including the token on a driven clock.
0.2.122
-------
  The trace now reports the BRANCHING FACTOR: "822,202 nodes (87%) making allthemodium_nugget
  via 12 patterns". Pattern identity is a per-item UUID, so two copies of one recipe are two
  alternatives to the calculator and each costs its own failing subtree. This is the number that
  decides whether deduplicating patterns is the fix, measured instead of assumed. Groundwork for
  the memoization idea, which was investigated and REJECTED AS UNSOUND -- see CHANGELOG.
  traceCheck 17 -> 20.
0.2.121
-------
  Two fixes the first real traces exposed. (1) Percentages were computed against the TOTAL node
  count while the counts only cover nodes after the detail threshold, so a calculation that had
  just crossed the line reported its dominant resource as "4%" when it was ~99% of everything
  actually seen. Now relative to observed nodes, and the header says when the breakdown is
  partial. (2) The threshold drops 100,000 -> 20,000 and becomes traceDetailThresholdNodes:
  real stalls of 91,807 and 97,967 nodes got no breakdown at all while a 104,327-node one that
  did turned out to be the identical problem. A threshold set above the thing you are trying to
  see is worse than no threshold. traceCheck 14 -> 17.
0.2.120
-------
  traceSlowCalculations: breaks down a stalled crafting calculation instead of only timing it.
  RS reports MISSING_RESOURCES and nothing else -- no resource, no indication where the time
  went, and identical to "cannot be made" -- so acting on a 5s stall has meant guessing, three
  times wrongly this session. The listener RS already drives carries both facts:
  childCalculationStarted fires once per tree node, ingredientsExhausted names what a branch ran
  out of. Logs the root resource and amount, the node count, and the resources the search spent
  itself on and kept exhausting. The per-resource map only starts after 100,000 nodes, so a
  normal craft pays one increment and only a pathological one pays for detail; the resource name
  is a supplier so it is never even formatted below that. New traceCheck (14), wired into build,
  confirmed to fail 5 of 14 with the threshold guard removed.
0.2.119
-------
  The timeout counter added in 0.2.118 never counted anything. It tested elapsed >= the
  configured budget exactly, and a calculation that burns the whole budget measures just UNDER
  it: RS polls its cancellation token rather than interrupting, and elapsed nanos truncate on
  integer division. The report showed "4,999ms session peak" beside no timeout line at all.
  Now allows 50ms of tolerance -- nothing else lands that close to the ceiling by chance.
0.2.118
-------
  Reporting fix, no behaviour change. 0.2.117 printed the session-wide slowest calculation
  beside per-window deltas, producing lines like "187 craft calculations (0.69ms mean, 5,000ms
  slowest, 129ms total)" where the peak cannot fit inside the total -- the exact "untrue for
  half the line" flaw ChatReporter's own javadoc warns about. It is now labelled "session peak",
  and the per-window question is answered by a new counter: "N hit the calculation timeout",
  compared against craftingCalculationTimeoutMs rather than a literal 5000. Each one is also a
  craft reported impossible that may only have been slow.
0.2.117
-------
  sortPatternsByPriority: the ROOT CAUSE of the whole session. RS 2.0.9 keeps each output's
  patterns in a PriorityQueue and reads them with holders.stream() -- and PriorityQueue
  guarantees order only for its HEAD, so every alternative after the first comes back in raw
  heap-array layout, which depends on the sequence patterns were added in. CraftingTree tries
  them in that order and explores each failure to exhaustion, so an arbitrary order is an
  arbitrary cost. Re-adding patterns (moving them into one provider) reshuffles every heap:
  same patterns, 0.199 -> 20.249 ms/tick. Now sorted by priority, tie-broken on the pattern's
  UUID rather than an insertion counter, so a pattern keeps its place when it MOVES. New
  patternOrderCheck (29) plus a gametest against RS's real repository (10 total), confirmed to
  fail with the sort off: "insertion sequence 1 produced a different search order".
0.2.116
-------
  The expensive calculations FAIL, they do not succeed - 0.2.113 had it backwards, and the
  direct measurement it added is what proved it. "slow crafts backed off" never appeared once,
  while the mean hit 387ms and the slowest pinned at exactly 5,000ms = RS's
  TimeoutableCancellationToken.TIMEOUT_MS. So the original failure-only premise was right; what
  was wrong is the ladder, which cannot bound a variable cost. A slot that burns 5s and then
  sleeps the 200-tick cap still eats a third of the thread. stepRequesterBudgetPercent (default
  5) derives the sleep from the cost instead: a slot may occupy at most 5% of the server thread,
  so a 5,000ms timeout sleeps 100s and a 70ms call sleeps 1.4s. Applied as a floor on the ladder,
  never a ceiling. stepRequesterCostCapTicks (6000) stops it becoming permanent silence.
  CONFIG TRAP: NeoForge does not rewrite an existing config when a default changes, so
  0.2.115's 10 -> 1 never reached the live file. Edit it by hand or delete it to regenerate.
0.2.115
-------
  0.2.113's threshold was wrong by two orders of magnitude and this measures instead of
  guessing. The 10ms came from reading "LP planner declined" as one line per calculation
  (~1/s) against 34.8% of the thread, giving ~400ms per plan. That line is per distinct
  resource offered to the LP planner, not per call. Profile KJdBQvnix4: 60,580ms inside the
  timed region over 120s with exactly ONE call above 10ms -- thousands of few-millisecond
  calls, not a handful of enormous ones. Result in game: "slow crafts backed off: 1".
  /rstweaks stats now prints craft-calculation count, mean, slowest and total, and the
  default drops 10 -> 1. No mechanism change; the branch was always firing correctly.
0.2.114
-------
  Tests for 0.2.113. The backoff decision moved out of StepRequesterNetworkNodeMixin into
  SlotBackoff - no Minecraft, RS, mixin or config types - so a plain JVM can exercise it;
  plannerCheck can never test a mixin, but it can test this. New `backoffCheck` task, 59
  assertions across 15 scenarios, wired into `check` so `build` runs it. Confirmed to have
  teeth: reinstating the pre-0.2.113 unconditional reset fails 32 of the 59. No behaviour
  change. What it still cannot prove is that the redirects fire or that the timing is real -
  that needs the game.
0.2.113
-------
  stepRequesterSlowCalculationMs: the Step Requester backoff now triggers on COST, not just
  on failure. The old mixin reset a slot on any success, on the premise that only failed
  attempts are expensive. Disproved 2026-08-23: three Step Requesters held 34.8% of the
  server thread while just 45 attempts failed in 100s, and plan-copies-avoided rose 72.6M in
  45s. The costly calculations SUCCEED, so each reset its own backoff and reran next tick.
  A success slower than the threshold (default 10ms) now sleeps on the same escalating
  ladder. Fast successes are untouched. Exposed as "slow crafts backed off" in chat.


0.2.112
-------
  craftingCalculationTimeoutMs: RS's TimeoutableCancellationToken allows 5000ms per crafting
  calculation, and that is five seconds of the SERVER THREAD - a doomed request freezes the
  world for a hundred ticks before reporting failure. Now configurable. DEFAULT IS RS'S 5000
  AND CHANGES NOTHING: a cancelled calculation is indistinguishable from an impossible one,
  so lowering it can silently refuse legitimate large crafts. Lower deliberately, a step at
  a time. Confirmed by profile o7HhlSJezm, where 0.2.111 dropped ensureTaskForCraftableAmount
  from 98.07% to 0.30% and left the first calculation itself at 50%, bounded only by the 5s.

0.2.111
-------
  boundCraftableSearch: RS runs binarySearchMaxAmount with CancellationToken.NONE, discarding
  the caller's timeout at the most expensive step of a craft request - every probe is a full
  recursive calculation. Measured at 98% of a server thread from one Cable Tiers exporter. Now
  passes the real token. First rstweaks fix that bounds COST rather than frequency.

0.2.110
-------
  /rstweaks stats now NAMES the resources the network keeps failing to autocraft. A profile
  showed 92.4% of the server thread was one autocrafting Exporter re-running a full crafting
  calculation; the uncraftable cache bounds how often, never how expensive. Finding that
  exporter is the only real fix, and nothing in game said what it was asking for.

0.2.109
-------
  lazyPatternPlanCopy now shares the OUTER ingredients map as well as the inner ones. The first
  pass left copy() still rebuilding the outer map entry by entry - 66.9% of the method was its
  own loop and 29.2% HashMap.put, while the existing share cost 0.05%. copy was 39% of the
  server thread on the profile this came from. Same invariant, same kill switch.

0.2.108
-------
  A Refined Storage External Storage pointed at a Mekanism QIO Dashboard now reads and
  writes the QIO (#12). Stock cannot: External Storage attaches to an IItemHandler
  capability and a QIO's contents live in a frequency, not in the block, so the storage
  reads as empty. Registered through RS's public addExternalStorageProviderFactory and
  Mekanism's published IQIOComponent/IQIOFrequency - no mixin either side, Mekanism
  optional. Two-way; use the External Storage's own Access Mode for read-only. Config:
  mekanismQioExternalStorage.

0.2.107
-------
  Clamp instead of wrap when a fluid amount will not fit in a FluidStack (#17). RS's
  VariantUtil.toFluidStack warns above Integer.MAX_VALUE and then casts anyway, so a large
  amount arrives NEGATIVE - which is why a 2.1 MB fluid could not be bucketed out of a grid even
  in stock RS. Clamping fixes both the canExtract check and the real ENTIRE_RESOURCE transfer,
  so shift-fill on such a fluid is back to one operation per transfer rate instead of the 64 B a
  click the bucket fallback allowed. The client asks whether the clamp actually applied by
  running the conversion, rather than assuming, and keeps the slow path when it did not.

0.2.106
-------
  A fluid the network holds billions of could not be picked up, and the tank got stored instead
  (#17; ~2.1 MB of XP fluid from a Just Dire Things experience holder). RS's canExtract offers
  the container the ENTIRE network total and fillContainer narrows it to an int, so past
  Integer.MAX_VALUE the tank is handed a NEGATIVE FluidStack, returns 0, and is judged unable to
  hold that fluid. The fill decision no longer asks canExtract at all - it asks whether the
  container is the right KIND for the row, which does not involve an amount. Shift-fill above
  that line uses bucket-sized transfers, the only ones that survive the conversion. Being too
  permissive costs a click that moves nothing; being too strict cost the player their tank.

0.2.105
-------
  0.2.104 made #17 LESS reliable, so it can no longer be the only answer. The recorded slot
  rectangles are now a preference, not a requirement: when no rectangle matches the click, the
  row falls back to the one Refined Storage itself resolved, so behaviour is 0.2.103's rather
  than worse. Restores the blank-area right-click hook 0.2.104 dropped. Adds a diagnostic line
  under logGridViewDiagnostics reporting cells recorded, cell hit, stale row, resolved row and
  canExtract - read that before theorising about this again.

0.2.104
-------
  Fixes "sometimes it won't fill and just inserts if I hover too fast" (#17). RS assigns the
  clicked row while RENDERING, so a click that beats the next frame is answered with the last
  frame's hover - stale or -1 - and falls through to the insert branch, putting the tank in the
  network. Container clicks are now resolved from the coordinates the click carries, against
  slot rectangles recorded as RS draws them, so no layout math is duplicated. The hook moved up
  to the click router because the routing was what was wrong.

0.2.103
-------
  Shift-click now sends its operations together in one tick instead of one per tick until the
  cursor stack stopped changing (#17). GridContainers divides the container's contents, or its
  free space, by what one operation moves - both measured by simulating that operation against
  the container, so no tier table is baked in and a tank from any mod answers correctly.
  Anything that will not give a number falls back to a single operation. Chemicals get the
  same arithmetic through reflective IChemicalHandler handles.

0.2.102
-------
  Fixes 0.2.101, which also stored the tank itself on every container click (#17).
  CompositeGridInsertionStrategy's tryAlternatives does not mean "try harder after failing" -
  the fluid and chemical strategies ARE the alternatives and the default is the item strategy,
  so passing false goes straight to putting the tank in the network. Every insert now passes
  true; storing an EMPTY tank as an item still works, because the fluid strategy declines it
  and the default runs after. Left-click also no longer inserts at all - it only fills the
  container from a row it can accept.

0.2.101
-------
  Grid clicks that make sense while holding a tank (#17). With a fluid or chemical container
  on the cursor: left-click fills it by one bucket, right-click empties one bucket into the
  network, shift on either repeats until nothing more moves. Right-click on the fluid's own
  row now dumps, so a tank no longer has to be emptied by finding blank grid space. Stock
  "left-click = everything" never emptied a tank and could not: Mekanism hands over one tier
  transfer rate per operation, 64 B from an Ultimate that holds 256 B, so emptying one is the
  same operation repeated. Config: containerGridClicks.

0.2.100
-------
  Functional Storage's drawer denylist check cached per item. BigInventoryHandler asks the
  tag TWICE per insert attempt - insertItem, then again inside the isValid it calls - and
  the set probe under it was 11.6% of LavaSurf's server thread, the second largest self
  frame. A tag holds items, so the answer cannot depend on components or count; cached on
  the item and dropped whole on TagsUpdatedEvent, which is the only thing that changes a
  tag. No staleness window. Config: cacheDrawerDenylist.

0.2.99
------
  Sophisticated Storage's failed-insert cache made able to hit. It remembers rejections
  by OBJECT IDENTITY, and RS builds a fresh ItemStack per attempt, so it never found its
  own entry and every attempt rescanned the whole barrel: 54% of the server thread on
  LavaSurf's profile, under one autocrafting task returning outputs. Second record keyed
  by item+components. Rejections only, per-tick, also cleared on any extraction - which
  upstream does not do. Config: cacheFailedInsertsByValue. Worth reporting upstream.

0.2.98
------
  BUG FIX: hard server crash on opening any grid or starting any autocraft, on a network
  whose cached total for one resource had overflowed past Long.MAX_VALUE and wrapped
  negative. MutableResourceListImpl.Entry.increment validates the amount being added and
  never the sum; it is the only unguarded route into that field. The total now saturates
  instead of wrapping, and is logged once per resource, naming the resource. Reported by
  LavaSurf 2026-08-18 (crash on the Step Requester, then on every grid open, surviving a
  relog). New gametest reproduces the exact crash with the clamp disabled.

0.2.97
------
  Two more plannerCheck scenarios (52 total), no behaviour change. 0.2.96 tested the
  BranchAndBound contract directly; these drive PlanMatrix with a starved budget on a graph
  known to plan, and assert on the literal "no integer solution" string that
  LpCraftingPlanner matches to set impossible. That coupling is what broke, and nothing was

0.2.96
------
  BUG FIX: some late-game crafts could not be started at all -- Mekanism Teleportation
  Core and the ATM Star fragment recipe were the reported ones. The list preview said the
  craft was impossible and greyed out Start; switching the preview to TREE worked around
  it, because the tree preview is not hooked. Cause: the LP solver returned "no integer
  solution" when it had only hit its depth, node or pivot cap, and the preview treats that
  as proof. Budget exhaustion is now a decline, which falls through to stock RS.

0.2.95
------
  CORRECTION to 0.2.93's diagnosis, no behaviour change. The duplicate-task flood does NOT
  need a regulator upgrade, which is what 0.2.93 claimed. The common cause is the network
  not being able to craft as many as the exporter asks for: RS clamps the request to what
  is craftable now (say 1), and 1 never reaches the quota (say 64), so every following
  request starts another one-item task. Measured: 12 requests, 12 tasks, same resource, no
  regulator. `waitForRunningCraft` already fixed both; only the config text, the mixin
  comment and the tests were wrong about why.

0.2.94
------
  `/rstweaks stats` prints one counter per line under a header, instead of a dozen
  figures run together on one wrapping line. The periodic chat broadcast is now OFF by
  default (`chatNotificationIntervalSeconds` 0) and the join message no longer carries
  counters -- nothing posts them unprompted any more. Both at Wraith's request.
  The join line still announces version and active features.

0.2.93
------
  An autocrafting request waits for the craft already running for that resource (#14),
  behind `waitForRunningCraft` (default on). Stock RS only refuses a duplicate when the
  amount asked for is covered by what is running -- fine for a plain or tiered exporter,
  whose quota is a constant 1 or 64, but a REGULATOR upgrade asks for the whole
  outstanding shortfall, which grows as the destination drains, so every increase starts
  another task. Measured: 20 requests, 20 tasks for one resource. Now 1.

0.2.92
------
  Gametests for the paths that only fail in game, runnable without a human (issue #2).
  `./gradlew runGameTestServer` boots a dedicated server with Refined Storage staged in,

  Covers a crafting task stepping and delivering its output, the Crafting Grid refill's
